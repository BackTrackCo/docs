The `@x402r/core` package includes a condition builder for creating complex access control logic.

## Overview

Conditions control who can perform actions on payments. The SDK provides builders for composing conditions:

```typescript
import { conditions } from '@x402r/core';

// Create a condition that allows receiver OR arbiter
const accessCondition = conditions.or([
  conditions.RECEIVER,
  await conditions.staticAddress(arbiterAddress),
]);
```

## Singleton Conditions

Pre-deployed singleton conditions for common use cases:

```typescript
import { conditions } from '@x402r/core';

// PayerCondition - allows only the payer
conditions.PAYER

// ReceiverCondition - allows only the receiver
conditions.RECEIVER

// AlwaysTrueCondition - allows anyone
conditions.ALWAYS_TRUE
```

### Usage

```typescript
// Use RECEIVER for release conditions
const releaseCondition = conditions.RECEIVER;

// Use PAYER for refund conditions
const refundCondition = conditions.PAYER;
```

## staticAddress

Create a condition that allows a specific address:

```typescript
const arbiterCondition = await conditions.staticAddress(
  publicClient,
  arbiterAddress
);
```

<Note>
`staticAddress` deploys a new contract if the condition doesn't exist yet. The address is deterministic (CREATE2).
</Note>

## Logical Combinators

### and()

Require ALL conditions to pass:

```typescript
// Both payer AND arbiter must agree
const condition = conditions.and([
  conditions.PAYER,
  await conditions.staticAddress(publicClient, arbiterAddress),
]);
```

### or()

Require ANY condition to pass:

```typescript
// Either receiver OR arbiter can act
const condition = conditions.or([
  conditions.RECEIVER,
  await conditions.staticAddress(publicClient, arbiterAddress),
]);
```

### not()

Invert a condition:

```typescript
// Anyone except the payer
const condition = conditions.not(conditions.PAYER);
```

## Complex Compositions

Combine conditions for complex access control:

```typescript
import { conditions } from '@x402r/core';

// Refund allowed by:
// - Payer OR
// - (Receiver AND Arbiter approved)
const complexCondition = conditions.or([
  conditions.PAYER,
  conditions.and([
    conditions.RECEIVER,
    await conditions.staticAddress(publicClient, arbiterAddress),
  ]),
]);
```

## Factory Utilities

Compute and deploy condition contracts:

```typescript
import {
  computeStaticAddressConditionAddress,
  getOrDeployStaticAddressCondition,
} from '@x402r/core';

// Compute address without deploying
const address = computeStaticAddressConditionAddress(designatedAddress);

// Deploy if not exists
const conditionAddress = await getOrDeployStaticAddressCondition(
  publicClient,
  walletClient,
  designatedAddress
);
```

## Example: Payment Operator Configuration

```typescript
import { conditions, getOrDeployPaymentOperator } from '@x402r/core';

// Configure operator with custom conditions
const operatorConfig = {
  feeRecipient: feeAddress,

  // Only receiver can release
  releaseCondition: conditions.RECEIVER,

  // Payer OR designated arbiter can request refund
  refundInEscrowCondition: conditions.or([
    conditions.PAYER,
    await conditions.staticAddress(publicClient, arbiterAddress),
  ]),

  // Use escrow period recorder
  authorizeRecorder: escrowRecorderAddress,
  releaseRecorder: escrowRecorderAddress,
};

const operatorAddress = await getOrDeployPaymentOperator(
  publicClient,
  walletClient,
  operatorConfig
);
```

## Best Practices

<AccordionGroup>
  <Accordion title="Use singletons when possible" icon="recycle">
    Prefer singleton conditions (`PAYER`, `RECEIVER`) over deploying new contracts when possible.
  </Accordion>

  <Accordion title="Keep compositions simple" icon="minimize">
    Deeply nested conditions increase gas costs. Keep logic as simple as possible.
  </Accordion>

  <Accordion title="Test conditions" icon="flask">
    Always test condition logic before deploying operators to production.
  </Accordion>
</AccordionGroup>
